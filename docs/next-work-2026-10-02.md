## 1. Automated compatibility and reliability — first

### Why this is worth doing

The current suite has 89 passing tests, mostly selected examples. The matcher,
configuration graph, profile selection, and pack state have interacting cases
that are suitable for independent generated tests. This can find defects and
provide the infrastructure for larger features without requiring a focused
application or typing into the user's desktop.

[Proptest](https://proptest-rs.github.io/proptest/intro.html) generates inputs and
reduces failures to smaller reproductions. Start there with a small independent
reference model. Add [cargo-fuzz](https://rust-fuzz.github.io/book/cargo-fuzz.html)
only for identified parser/rendering targets where coverage-guided mutation
adds value. These are complementary to concrete regressions, not replacements.

### Bounded first slice

- Extract only the pure-core seams needed by tests; avoid a daemon-wide rewrite.
- Test literal matching against a small independently written suffix model.
  Generate Unicode input, overlapping triggers, terminators, boundaries,
  backspaces, reset events, and empty match sets. Add regex cases with explicit
  expected suffix/capture behavior rather than pretending a literal model covers
  regex semantics.
- Test invariants: bounded retained input including zero enabled matches; no
  expansion for an ambiguous trigger; deletion counts limited to the matching
  suffix and documented terminator; cursor metadata inside the output; reset
  and profile changes discard stale partial triggers.
- Generate valid and invalid nested-variable graphs. Bound graph size during
  generation; explore deep chains and branching separately with process time
  and memory limits. Check cycles, missing references, output growth, and that
  dates in one expansion share the same instant.
- Compare schemas and the CLI on generated supported data shapes. Maintain an
  explicit list of semantic checks that only the CLI performs; schema success
  must not be mistaken for full validity.
- Inject file-operation failures into pack updates and config reloads using
  disposable directories and controlled adapters. Assert that the last valid
  configuration and installed pack remain recoverable. Never fault-inject into
  actual user configuration.

Code inspection points to `Expander::push_char`, case-sensitive duplicate
counting versus case-insensitive matching, recursive `render`, and the sequence
of filesystem renames in `packs::update_one` as useful targets. These are test
hypotheses, not confirmed defect reports in this planning pass.

### Acceptance and compute budget

Use reproducible seeds, persist minimal failing cases, and convert each defect
into a regression test before fixing it. Keep a bounded smoke run in ordinary CI
and provide an explicit extended test command for larger runs. Record case count,
seed, duration, covered properties, and failures. Set resource limits before
long fuzz runs. Stop increasing effort when it no longer adds meaningful case
or code-path coverage; do not imply that passing fuzz tests proves correctness.

First delivery: generated matcher tests, reproduced fixes if any, and a readable
report. Add graph and filesystem failure tests as separately reviewable slices.
This work needs no live desktop interaction. Do not expand it into an unbounded
security audit or full compositor emulator.

## 2. Echo variables — next visible feature

Let users define a name/signature once and reuse it across snippets. The current
renderer uses ordered replacement, whereas Espanso also supports interpolation
inside parameters and variable dependencies. Define that contract before coding.

- Support literal `echo` and a documented subset of parameter references.
- Make evaluation order explicit; detect cycles and missing references, preserve
  intentional literal braces through a defined escape mechanism, and do not
  introduce shell/script execution.
- Update schemas, `check`, preview, documentation, and pack compatibility reports
  together. Use exact-output fixtures from the supported semantics.
- Do not claim full Espanso variable parity or automatically import unsupported
  packs. Full personal configuration migration remains a later task.

The existing [research findings](ai-research/20261001-autonomous-feature-priorities/findings.md)
and [Espanso variable documentation](https://espanso.org/docs/matches/variables/)
explain the dependency/escaping issue. Recheck upstream semantics at implementation.

## 3. Named personal snippet groups — larger feature

Add enable/disable controls for personal work, language, or project collections.
Pack toggles already exist; reuse the appropriate concepts rather than duplicating
pack state. Define precedence between groups, profiles, and packs, behavior when
a disabled group owns a nested reference, persistence, and duplicate resolution.

Deliver configuration/CLI/IPC plus state-transition tests first. Add plugin
controls afterwards with a focused UI check. This is a better substantial
product addition than random greetings or another small generator, but requires
more design than echo.
